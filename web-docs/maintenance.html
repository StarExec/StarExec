Redeploying StarExec

My (Jack’s) experience maintaining StarExec on the head node has mostly consisted of “re-deploying” StarExec after code changes and restarting Apache (web server) or Apache Tomcat (java web framework server that normal apache forwards to) when they’re down.
  • First ssh into the head node as your user. You can then switch users to become the tomcat user which hosts everything using
  • sudo su - tomcat
    You’ll have to enter the long weird tomcat user password at this point.

  • As tomcat, you’ll find the main StarExec code directory under “~/StarExec-Deploy”: 
    cd ~/StarExec-Deploy

  • You can rebuild and redeploy using the following incantation from within that directory: 
    ant build -buildfile build.xml; script/soft-deploy.sh

  • If ever there is a problem with tomcat, it would normally be restarted using 
    sudo /usr/bin/systemctl status tomcat7 
sudo /usr/bin/systemctl stop tomcat7
sudo /usr/bin/systemctl status tomcat7 
sudo /usr/bin/systemctl start tomcat7 
sudo /usr/bin/systemctl status tomcat7
    Note that you have to use the full path /usr/bin/systemctl. We used to offer this alternative, but Pedro says to not use it: 
    /project/apache-tomcat-7/bin/shutdown.sh
/project/apache-tomcat-7/bin/startup.sh

  • To see the state of SGE queues: 
    qstat -f | less

Fixing Compute Nodes and Database

  • To remove an error flag (E) from an SGE queue, as user ‘jam771’ (or any other user with the privilege to run this) run the following, for example: 
    sudo qmod -c all.q@n001.cluster.edu

  • Restarting frozen compute nodes 
    #----kill all "dr" and "Eqw" jobs
qstat -u '*' | awk '$5 == "dr" {print $1}' | xargs -I {} qdel -f {}
#----restart SGE engine on the nodes
sudo su -
root> for n in {001..032}; do echo n${n}; ssh -o ConnectTimeout=1 n${n} service sgeexecd.p6444 restart; done

  • Cleaning the SGE queues 
    Disable or enable SGE (Son of Grid Engine) node on StarExec
1. List all nodes in queue
> /cluster/gridengine-8.1.9-2/bin/lx-amd64/qconf -sel
...
n030.cluster.edu
n031.cluster.edu
n032.cluster.edu
se-m1
2. Disable nodes
sudo su -
root> for n in {001..032}; do echo n${n}; /cluster/gridengine-8.1.9-2/bin/lx-amd64/qmod -d all.q@n${n}; done
root@se-m1 changed state of all.q@n032.cluster.edu (disabled)
3. Confirm node is disabled (states contains "d")
> qstat -f | egrep -A 1 "states|n030|n032"
queuename qtype resv/used/tot. load_avg arch states
 State Code  Meaning
 u           Unknown (execd not responding)
 a           Alarm state (load threshold exceeded)
 d           Disabled (admin disabled via qmod -d)
 s           Suspended (queue manually suspended)
 E           Error (comm failure, daemon down, etc)
 -           OK (enabled and available) 
4. Enable node (I disabled n030 again after confirming .)
sudo su -
root> for n in {001..032}; do echo n${n}; /cluster/gridengine-8.1.9-2/bin/lx-amd64/qmod -e all.q@n${n}; done
5. Confirm node is enabled (states contains "-")
> qstat -f 
6. Optionally restart the SGE master
> sudo service sgemaster.p6444 restart

Cleaning the Database

0th, you want to delete the old jobs (/starexec/starexec_db_cleanup/delete_a_users_jobs.py)
1st, you have to stop starexec (/project/apache-tomcat-7/bin/shutdown.sh)
2nd, you have to export the database contents to a file: 
mysqldump -u se_admin -pdfsdf34RFerfg3TFGRfrF3edFVg12few2 starexec > /starexec/data_dir/jacks_db_backup2
3rd, kill the database service (service mariadb stop)
4th, you should backup the /var/lib/mysql/ibdata1 and possibly other files there.
I think now you just delete the ibdata1 and other files to make mariadb start from a blank slate...but maybe I'm wrong about this part...
5th, restart mariadb (service mariadb start)
6th, restore your earlier sql backup: (mysql < /starexec/db_backup/mysql_backup_2025-5-5.sql)
7th, restart all your services and redeploy.

Installing Software

  • Option 1 (preferred) - as a user
    • Install software to cluster shared filesystem (/starexec) and create a module for it (or update your .bash_profile).
    • All members of the sutcliffe IDSC Project (LDAP group) can:
      • install software in /starexec/sw/sutcliffe.
      • create modules in /starexec/sw/lmod/lmod/modulefiles/Sutcliffe
      Current members of sutcliffe group are you, jack and me.

  • Option 2 (dangerous) - as root
    • Use yum “download only” plugin to save the rpm’s to a shared space, then a loop to push the packages to all the nodes.
    • Installing packages with yum has the potential of bricking the cluster environment, so only root can push yum packages to nodes. Pedro granted Geoff's account privilege to run the yum commands below on the head node and Pedro can also grant Geoff privilege to run on the compute nodes. Pedro cautions against this though because the software and hardware is long since out of support.
    • Example installing git on all nodes using yum
      • Download the rpms 
        [pdavila@se-m1 ~]$ sudo /usr/bin/yum install --downloadonly --downloaddir=/cluster/rpms/sutcliffe/git git -y
      • Install on head node 
        [pdavila@se-m1 ~]$ sudo /usr/bin/yum --disablerepo="*" localinstall /cluster/rpms/sutcliffe/git/*.rpm -y
      • Disable all the dead repos, or yum commands will hang indefinitely. 
        [root@se-m1 yum.repos.d]# for n in {001..032}; do echo "n${n}"; ssh n${n} 'mv /etc/yum.repos.d/CentOS* /etc/yum.repos.d/disabled'; done
        Pedro also added the Vault repo to the compute nodes to address any issue that may arise from inconsistences with packages installed on head node and those installed on compute nodes. 
        [root@se-m1 yum.repos.d]# for n in {001..032}; do echo n${n}; scp CentOS-Vault.repo n${n}:/etc/yum.repos.d/ ; done
      • Install on compute nodes (using xCat's CentOS 7 repo)
        [pdavila@se-m1 ~]$ sudo /opt/xcat/bin/psh n001-n032 yum install ncdu -y
